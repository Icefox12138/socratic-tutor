# 架构分析：对《苏格拉底式 RAG 教学 Agent 设计 v1.3》的独立复核

> 复核对象：`docs/DESIGN.md` v1.3（2026-10-28，1,787 行）；本次按复核结论补入 §12.9/ADR-12，形成 v1.4（2026-10-29，1,912 行）。
> 复核日期：2026-10-29
> 性质：**架构分析与风险复核，不是实施文档**。不重复 DDL、接口、命令；只回答"这个设计能不能按计划成立、哪里最可能失败、先验证什么"。
> 方法：把设计中的"承重假设"逐条抽出来，用算术、环境实测、依赖元数据和 DSH 文档对照；不能验证的明确标"待实测"。

---

## 0. 复核结论

### 0.1 一句话

**设计是可执行的，而且质量高于大多数个人项目；真正的关键路径不是代码，而是数据质量与三个未验证的平台假设。** 建议批准 P0，但把 P0 当成"否决性实验"，而不是"开工仪式"。

### 0.2 五个承重假设

| # | 假设 | 设计中的依据 | 若不成立的后果 | 复核判断 |
|---|---|---|---|---|
| A1 | 330,519 影印页可在 92–184 h 内 OCR 完 | §0、§8.2、§19 | 按需入库策略失效，P1/P3 排期整体后移 | **口径冲突（1–2 页/秒 vs 0.5–1 页/秒），必须实测**（见 §4） |
| A2 | `dsh-knowledge` 能关掉自动检索、并按 chunk 隔离答案 | §16.10、§23.3–23.4 | 答案进入学生上下文，苏格拉底立刻失效 | **高风险**：插件无 chunk 级 `visibility`，只能靠三 base 变通 |
| A3 | 8 GB 显存能同时承载嵌入、OCR、VLM，且 p95 < 8 s | §2.1、§3.4、§9.2 | 吞吐不达标或频繁 OOM | **需调度器**；本地模型只能做分类，主模型在远端 |
| A4 | DSH 0.2.1-rc.3 具备 8 项扩展点，尤其"改写即将发出的助手消息" | §16.9 | 泄漏只能靠数据层，critic 无法兜底 | **大概率只有部分成立**；§2.3 已承认没有公开钩子 |
| A5 | 5 种语言 × 3 个学科可在 243 h 内做出 MVP | §1.1、§19 | 范围膨胀，每个分支都半成品 | **建议收窄**：先做人文 + 中文 + 一本书 |

### 0.3 三个最高风险

1. **答案隔离不是端到端的**：数据层（L1）没有 chunk 级可见性，宿主层（DSH）没有出站改写钩子，中间只剩"三 base + 提示词 + critic"。这是全系统最重要的不变量，不能靠约定。
2. **竖排古籍的注文分离**：这是项目里最难的一步，却被排在 P3（第 11–14 周）并用 24 h 估算；如果它不达标，二十四史/十三经/金庸这条主线无法引用。
3. **规模假设没有基准**：801 本、361,862 页、91.3% 影印，这些数字很硬；但"多少页/秒、多少小时、多少 chunk、多少 GB"目前是推算，不是实测。

### 0.4 建议

- **批准 P0，但设置 6 个 go/no-go 门槛**（见 §14）；任一不过，走 B 分支或收窄范围。
- **把"答案隔离"提升为 sidecar 的第一契约**，不要把它托付给 L1 插件的配置项。
- **先做 60 页解析基准，再决定是否碰 801 本**；不要用全库 OCR 验证解析器。
- **MVP 收窄到"人文 + 中文 + 一本书 + 一个学生"**；Steadman 希腊/拉丁作为第二垂直，理工/乐理后置。
- **教学范式补一层**：§12.9 已补"示范→完成→独立"；P2 前用两篇同难度文本做 guided/strict 小实验，别把"提示时机"当成"教学策略"。

## 1. 复核范围与方法

### 1.1 看什么、不看什么

- 看：目标与约束是否自洽；架构是否能承载教学目标；关键路径上的量化假设；DSH 集成与许可边界；评测能否证伪。
- 不看：DDL 字段命名、API 路径拼写、UI 组件细节；这些属于实现评审，不是架构分析。
- 不做：没有运行代码、没有安装插件、没有解析 PDF；所有"实测"只到环境与依赖元数据层（见附录 A）。

### 1.2 设计本身的优点（先说清楚）

- **ADR-03（确定性状态机）和 ADR-05（答案物理隔离）是全篇最重要的两个决策**，方向正确；多数同类项目会败在"用 prompt 装苏格拉底"。
- **三流分离（原文/词表/注释）** 不是过度设计，而是古典语文学教学的硬需求；把注文当经文引用是学术错误，不是体验问题。
- **按需入库** 与 **Gate 制** 符合单人、业余投入的现实；没有追求"全库一次做完"。
- **§23 的复用边界**（借存/切/嵌/搜，不借教/判/评）是成熟的工程判断；§24 的长程协议测试也抓住了教学 Agent 的真正难点。

下面的批评，都是在这个质量基线之上提出的。

## 2. 设计是否覆盖了原始需求

| 原始需求 | 设计中的承载 | 覆盖判断 |
|---|---|---|
| 开源 RAG / 知识库框架 | L1 复用 `dsh-knowledge`，Plan B 自建 Qdrant/FTS5（§23） | **强**，但受 AGPL 与可见性缺口拖累 |
| 书本 PDF 处理 | 五条解析路径 + 竖排五处理 + 三流分离（§8） | **设计强，验证弱**；竖排是最大不确定性 |
| 矢量化 / 多模态 | BGE-M3 dense + 页图按需 + VLM 困难页（§9、§15） | **基本覆盖**；古典语言嵌入质量未验证 |
| 扫描影印版 | PaddleOCR + MinerU2.5 + 质量闸门（§8.2、§8.6） | **覆盖**，但吞吐与 CER 目标需实测 |
| 联网搜索与范围框定 | 按主张类型分级 + 外部适配器（§10.2、§10.4） | **方向正确，但适配器偏人文**；代码平台/论坛/Zhihu 未落地 |
| 苏格拉底为主 | 确定性状态机 + L0–L5 + 揭示政策 + 反模式（§12） | **强**；`EVALUATE` 是薄弱点；v1.3 默认 ASK-first、缺支架策略（F11；v1.4 已补） |
| Python/Mathematica/LEAN 为辅 | SymPy 默认、Wolfram/Lean 可选（§14） | **合理**；沙箱与等价判定需加固 |
| 通过 DSH 插件构建 | 薄 Host 插件 + sidecar + 8 项 API 核对（§16） | **架构正确**；平台假设未验证 |

### 2.1 一个覆盖缺口：外部来源适配器偏人文

§10.2 的分级表提到了 GitHub、Stack Exchange、知乎；但 §10.4 的实际适配器只有 Perseus/Scaife、PHI、ctext、Logeion/LSJ/L&S、Wiktionary/汉典、arXiv/Crossref、Wikipedia。

- 对"人文 + 古典语言"这个首月垂直，够了。
- 对设计宣称的"文史哲 / 语言 / 理工"三学科，不够：理工需要 arXiv 全文、GitHub 代码、Stack Exchange、nLab/DLMF；这些目前只是分级表里的名字，不是适配器。
- 建议：**MVP 明确只承诺人文 + 古典语言**；把"代码平台/论坛/Zhihu"列为 P4，而不是隐含在分级表里。

### 2.2 另一个缺口：没有"学习增益"指标

§1.3 的 MVP 判据全是"合规/可回溯/延迟"，§20.3 也没有学习增益。这些指标能证明"系统没乱来"，不能证明"学生在学"。

- 不是要求 MVP 做教育实验；但至少在 P3 加一个 10 人以内的前后测，否则"苏格拉底有效"只是信念。
- 退一步，也应有"回讲通过率"和"同一概念 7 天后复测保持率"作为代理指标。

### 2.3 馆藏来源、Anna's Archive 与"知乎下限"

设计 §2.4 把合规边界写成"仅个人研读，不对外分发、不上传第三方 API"。这必要，但不充分：

- **法律**：个人学习用途的例外在各国范围不同；"自用"不等于"无风险"。馆藏文件名含 Anna's Archive 来源，说明至少有部分是影子图书馆下载。建议：
  - 每条 `book` 增加 `provenance`（自扫 / 公版 / 影子图书馆 / 购买）与 `license_status`（known / unknown / copyrighted）；
  - 影子图书馆来源只进本地 `personal` 分区，不进入任何可导出、可开源、可共享的索引；
  - 开源 fixture 只用公版文本；不要用馆藏书目或哈希清单做测试。
- **质量**：影子图书馆扫描件常缺版次、缺页、错页；引用时必须 `cite_verify` 回页图，不能只信 OCR。设计已有 `cite_verify` 工具，但应把它从"可调用工具"提升为"发布闸门"：S 级引用必须逐条通过。
- **可信度分层**：设计把知乎放 C（仅线索）、把 CSDN/百家号/盗版站放 D（禁止），这比原需求"知乎为下限"更严格，方向正确；但"按主张类型"要落到 `source_grade` 的返回值上，不能只做域名判断（§10.2 与 §16.3 的口径需要统一）。
- **原需求中的代码平台/论坛**：GitHub、Stack Exchange、知乎在 §10.2 只是分级示例，§10.4 没有适配器；如果 MVP 只做人文，先不补；如果要做理工，必须补 GitHub/StackExchange/arXiv 全文，否则"代码平台"只是名义覆盖。

## 3. 十一个关键发现

按"如果不处理，最可能让项目失败"排序。每条给：证据、影响、建议。

### F1（严重）答案隔离不是端到端的

**证据**

- ADR-05 要求"答案与提示物理隔离（`visibility` 字段 + 查询过滤）"。
- §23.3 自己承认 `dsh-knowledge` 只有 base/document 级边界，**没有 chunk 级 `visibility`**。
- §23.4 的变通是建 `student` / `tutor` / `answer_key` 三个 base，教学工具只查前两个。
- §2.3 又承认 DSH **没有公开的"改写即将发出的助手消息"钩子**。
- §16.3 说 `kb_search` "自动过滤 `answer_key`"，但过滤发生在我们自己的工具层，不是 L1 的强制边界。

**影响**

三个 base 只有在"调用方永远选对 base"时才成立。可破坏它的路径至少四条：

1. `dsh-knowledge` 的 `autoRetrieve` 默认开启；一旦没关干净，每轮自动注入的证据可能来自任意 base。
2. 模型可以通过工具参数或另一个工具（如通用 `knowledge_search`）绕到 tutor base；我们的 `kb_search` 过滤不等于 L1 过滤。
3. `translation` 流本身是 `visibility=answer_key`，但 `note` 流（注释）经常包含译文、解释、甚至答案；按 stream 过滤不等于按语义过滤。
4. 即使上下文里没有答案，模型也可能从参数化记忆里"猜"出答案；这不是隔离能解决的，但说明"没有出站钩子"时不能承诺零泄漏。

**建议**

- 把 `view=student|tutor` 作为 **sidecar `/v1/search` 的必填参数**，由 sidecar 在 SQL/向量过滤层强制；不要让模型或 Host 插件决定 base。
- `answer_key` base 不对模型暴露任何工具；只允许复盘/教师模式通过独立端点读取。
- 写一个 **canary 测试**：在 `answer_key` 和 `translation` 里埋唯一短语（如 `CANARY-7F3A`），用 hint level <4 跑 200 次检索与 50 轮对话，断言该短语从未出现在模型上下文与输出中。
- 如果 P0-0 证明 L1 无法做到，**不要用三 base 硬撑**；直接走 Plan B 自建检索（60–80 h），或把 L1 放到独立进程并用 HTTP 强制 view。

### F2（高）`dsh-knowledge` 的 AGPL 与"进程内调用"存在解释风险

**证据**

- npm 元数据：`dsh-knowledge@0.5.2`，`license: AGPL-3.0`；依赖含 `mupdf`、`ppu-paddle-ocr`、`onnxruntime-node`、`@huggingface/transformers` 等。
- §23.5 的处理是"只调用工具/HTTP，不修改、不分发"。
- 但 §23.2 说它的落地形态是 `ctx.knowledge` + `tool-knowledge` + `ui-knowledge` 三行 bundle——这是 **Cordis 进程内服务**，不是 HTTP 服务。

**影响**

"通过工具调用"是否构成 AGPL 的"组合/衍生"，法律上没有一句话结论；不同法域、不同律师会给不同答案。风险不在技术，而在你以后想 MIT 开源 `dsh-socratic` 时，是否会被认为整体应为 AGPL。

**建议**

- 在 P0-0 前做一个明确选择：
  - **要 MIT**：把 L1 作为**独立进程/HTTP 服务**（或直接用 Plan B），Host 插件只依赖 `knowledge_search` 契约。
  - **接受 AGPL**：把整个组合按 AGPL 发布，别再承诺 MIT。
- 不要既在进程内 import，又对外声称 MIT；这是自欺。
- 另外，npm 包 unpacked 4.2 MB / 221 文件，§16.10 的"单文件 22 MB"需要说明是构建后 bundle 还是估算；影响安装/分发判断。

### F3（高）Steadman 的字体分类规则覆盖不全

**证据**

- §8.4 的 `GREEK_FONTS = ("NewAthenaUnicode", "GFSPorson")`。
- 实测 `catalog.csv`（100 个 PDF）的字体列：`SPIonic` 至少出现在 6 个文档，`Gentium` 至少 3 个（若用于希腊文，最多 9 个），`SymbolMT` 6 个；此外还有 `GFSPorso`、`NewAthenaUni` 这类被截断的名字（catalog 的 fonts 字段有截断，首行恰好 80 字符）。
- `SPIonic` 是希腊语字体，`Gentium` 也支持希腊语；按现有规则，这些文档的原文会被判成 `gloss` 或 `note`。

**影响**

三流分离在至少 6 个 Steadman 文档上直接错分（SPIonic）；若 Gentium 也用于希腊文，最多 9 个。如果这些是首批精读文本（如 Cebes 残篇用 SPIonic），P0 的"申辩"闭环可能不受影响，但 P1 "Steadman 全量入库"会带错误。

**建议**

- 字体名只作为**先验**，真正分类用 **Unicode 区块 + 字体 + 位置**：
  - 希腊字母：U+0370–03FF、U+1F00–1FFF；拉丁扩展：U+0100–024F。
  - 字体名做前缀/模糊匹配，处理截断（`GFSPorso`、`NewAthenaUni`）。
- 做一次"每文档字体 census"，把非常见字体（SPIonic、Gentium、SymbolMT）列入 allowlist；未识别字体回退到 Unicode 判定。
- 在 P0 的 60 页基准里，至少包含 2 个 SPIonic、2 个 Gentium 文档。

### F4（高）E: 当前不可见，P0 的馆藏扫描被阻断

**证据**

- 本次复核：`Get-Volume` 只有 D:；`Test-Path E:\` 为 False；`E:\PDF` 不存在。
- 设计 §2.1 说 E: 465 GB、剩 50.6 GB、只读；§19 P0-3 要扫描 E:\PDF 的 801 本。

**影响**

如果 E: 是外接盘/加密盘/未挂载卷，P0-3 无法执行；如果 E: 已经丢失或盘符变了，整个"801 本馆藏"的基线要重做。

**建议**

- P0 前加一个 preflight：`Test-Path E:\PDF`、卷序列号、只读属性、可用空间；不通过就不启动 P0-3。
- 若 E: 是外接盘，把"挂载并锁定盘符"写进运行手册；不要依赖自动分配。
- 若 E: 暂时不可用，P0 先用 Steadman（D: 上 100 个 PDF，已实测 9,890 页 / 771 MB）跑通解析与检索，再补馆藏。

### F5（高）OCR 吞吐的算术不自洽

**证据**

- §0：330,519 影印页，OCR 需 92–184 h。
- §8.2：PaddleOCR PP-StructureV3（CPU，32 线程），1–2 页/秒。
- 算术：
  - 330,519 / 92 h = 3,593 页/h = **1.0 页/秒**；
  - 330,519 / 184 h = 1,796 页/h = **0.5 页/秒**。
  - 若按 1–2 页/秒，则应为 46–92 h，不是 92–184 h。

**影响**

这不是"保守一点"的问题，而是**单位口径不明**：1–2 页/秒是单进程、单页、理想版面，还是 32 线程聚合？如果是单进程，32 线程理论上可达 32–64 页/秒（实际受 I/O、内存带宽、版面复杂度限制，绝不会线性）；如果是聚合，92–184 h 又慢了一倍。

**建议**

- 用 100 页真实样本（竖排 30、横排扫描 40、公式/表格 30）测 **pages/s**，记录 CPU 利用率、内存、单页耗时分布。
- 排期用实测中位数，不要用"1–2 页/秒"这种区间。
- 把 OCR 吞吐作为 P0 的 Gate 之一（见 §14）；不达标就调整"按需入库"的书目数量，而不是硬扛全库。

### F6（高）竖排古籍的注文分离被低估

**证据**

- §8.3 的五个处理（列切分、双行注、校勘记、异体字、无标点）方向都对。
- §19 把它排在 **P3（第 11–14 周）**，P3-3 "史记一册竖排 OCR + 注文分离"仅 **24 h**，验收"注/正错分 ≤5%"。
- §21 自己把 R1（竖排 OCR）和 R2（注文混入）都标为"高概率、高影响"。

**影响**

竖排 + 双行注 + 校勘记 + 异体字 + 无标点，是古典文献数字化的深水区；24 h 更像是"跑通一册"的机器时间，不是"把错分率压到 5%"的研发时间。按经验，这个目标至少是 3–5 倍的工程量，且需要一本一本地调。

**建议**

- 把竖排解析**前移到 P1**，用 50 页人工标注做基准；不要等到 P3 才发现不可行。
- 分两级验收：
  - **可读级**：列序正确、正文可检索、注文可分离（错分 ≤10%）——P1 目标。
  - **引用级**：注/正错分 ≤5%、校勘记不进正文——P3 目标。
- 若 P1 只能做到"可读级"，产品上接受"竖排书只做页图 + 人工引用"，把自动注文分离降级为辅助。

### F7（中高）8 GB 显存与 p95 < 8 s 的组合需要调度器

**证据**

- §2.1：RTX 4060 Laptop，8 GB；只能跑 ≤2B 量化 VLM；ColQwen/7B 不做本地。
- §9.2：BGE-M3 dense 1024d，GPU batch 8–16；§8.2：PaddleOCR CPU；§15：页图 VLM 只用于困难页。
- §3.4：单轮 p95 < 8 s（不含长计算）。
- §24.3：本地模型只做分类，教学主模型在远端。

**影响**

- BGE-M3 fp16 约 1.1 GB 权重，加激活与 batch 可能 2–3 GB；VLM ≤2B 量化 2–4 GB；两者同时驻留就可能触顶，再加 OCR 的 GPU 后端（如果开）必 OOM。
- p95 < 8 s 里，检索 300 ms + 重排 200 ms 只占 0.5 s；剩下 7.5 s 要覆盖远端 LLM 的首 token + 生成 + 网络抖动。对 6k 上下文的 API 调用，这个目标偏乐观。

**建议**

- sidecar 内做**单 GPU 队列**：嵌入、VLM、重排串行；OCR 固定 CPU；不要在 FastAPI 多 worker 里各自加载模型。
- 把 p95 目标拆成"首 token < 3 s、完整回复 < 12 s"；流式输出比硬压总时长更现实。
- 记录每轮 `queue_wait`、`embed_ms`、`llm_ttft`、`llm_total`，否则无法定位 8 s 花在哪。

### F8（中）BKT 参数与反模式规则目前是"装饰性精确"

**证据**

- §12.5：`p_init=0.3, p_learn=0.15, p_guess=0.2, p_slip=0.1`，没有标定来源。
- §12.6：反模式"单轮 >1 个问号"——中文疑问句可以没有问号（"说说看"、"你觉得呢"）。
- §20.2：复盘 30 条抽检，§1.3 要求准确率 ≥80%。

**影响**

- 未标定的 BKT 会给学生显示"掌握度 0.62"这种看似精确、实际无意义的数字；一旦学生发现它不准，信任受损。
- 用问号数量判"提问轰炸"会漏判/误判；用 30 个样本估 80% 准确率，95% 置信区间约 ±14%，无法区分"80%"和"70%"。

**建议**

- BKT 先标为 **heuristic**，UI 显示三档（未掌握/在学/已掌握），不显示两位小数；积累 100+ 次作答后再标定。
- 反模式检测改为"疑问句分类器 + 规则"，或至少统计"吗/呢/？/请/说说"等标记。
- 复盘评估样本增加到 60–100 条，或报告置信区间；不要用 30 条得出"≥80%"的硬结论。

### F9（中高）Windows 沙箱与符号等价判定需要加固

**证据**

- §14.2：子进程执行，`timeout=20s`，内存上限 2 GB，单核，禁网；学生代码升级到 Windows Sandbox / WSL。
- §14.3：符号等价 `simplify(a-b)==0`，失败则 10 点数值采样。
- 当前 DSH 会话是 `danger-full-access` + 审批 `never`，不能依赖弹窗兜底。

**影响**

- Windows 上 `subprocess` 的 `timeout` 只杀直接子进程，不保证杀进程树；学生代码（或模型生成的代码）可以 fork 子进程逃逸，或用 `ctypes` 绕过内存限制。
- `simplify(a-b)==0` 不是判定过程：三角/对数/根式表达式可能化简不动，或返回非零但实际相等；10 点采样可能刚好避开奇点，给出错误置信。
- 20 s 对重型 SymPy 积分偏短，容易把"算得慢"误判为"算错"。

**建议**

- 用 **Windows Job Object** 包住子进程：`JOB_OBJECT_LIMIT_PROCESS_MEMORY`、`JOB_OBJECT_LIMIT_ACTIVE_PROCESS`、`KILL_ON_JOB_CLOSE`；超时用 Job 终止，而不是 `proc.kill()`。
- 符号判定顺序：`equals()`（带假设）→ 精确化简 → 数值采样（多点、避开定义域边界）→ 仍不定则 `unknown`；不要用单一 `simplify`。
- 显式计算工具超时放宽到 60 s；超过走 job，不占对话轮次。
- P0 做 6 个攻击测试：死循环、fork 炸弹、内存炸弹、写文件、联网、读 `E:`；全部拒绝才算过。

### F10（中）范围与工时口径不一致

**证据**

- §1.1 目标 G6（5 语言）、G7（3 学科）；§19 P0–P3 合计 **243 h**；§23.7 又说组合后 **210 h**（差 33 h，口径可能是是否含 P0）。
- §23.7 的模块工时相加是 210 h，但 P0 29 h 不在表内；P1+P2+P3 = 214 h，接近 210。
- §1.3 MVP 判据没有语言/学科覆盖指标，说明 MVP 实际上更窄；但目标表没有相应收窄。

**影响**

读者（尤其是接手的 AI Agent）会把 G6/G7 当成 MVP 承诺，导致范围膨胀；工时到底 210 还是 243 也会影响排期判断。

**建议**

- 明确写："MVP = 人文 + 中文（zh-Hant）+《史记》/《申辩》各一册 + Steadman 希腊/拉丁各 10 本；G6/G7 是产品目标，不是 MVP 验收"。
- 统一工时口径：P0 单列，P1–P3 用 214 h；§23.7 的 210 h 标"不含 P0"。

### F11（中）教学范式是 ASK-first，缺"示范→完成→独立"的支架

**证据**

- v1.3 的 §12.1 状态机是 `ASK` 优先：`ALIGN → DIAGNOSE → PLAN → ASK → WAIT → EVALUATE`，没有 `MODEL`/`COMPLETION`；v1.4 由 §12.9 扩展。
- §12.3 的 L0–L5 是"任务内提示阶梯"，不是"任务形态序列"；L2 的"例子"是提示，L4 是多次失败后的补救，不是新手的起点。
- §12.4 的 `may_reveal` 由 `attempts`/`frustration` 触发，不看先备知识。
- §12.5 的 BKT 记录掌握度，但不驱动"先示范还是先问"。
- v1.3 的 §12.7 `DisciplinePack` 只有 `plan/classify/hint/rubric`，没有 `demonstrate`/`completion`（v1.4 已补）。
- v1.3 全文检索 `guided / strict / worked example / 新手 / 先备 / 专家 / fading`，没有一处讨论教学支架策略（v1.4 已补）。

**影响**

- 对程序性任务的新手（语法解析、数学解题），"先问"容易造成无效摸索；提示阶梯只在失败后生效，救不了"连起点都没有"的学生。
- 设计的"强制回讲"其实就是一个很好的 self-explanation 机制，但它只接在 L4/L5 之后；如果把它接到 `MODEL` 之后，改动很小、收益很大。
- 对人文 MVP 影响相对小（论证可以靠追问），但对语言/理工分支影响大；如果 G7 要做三学科，这一层不能缺。

**建议**

- 在 §12 增加"教学支架策略"（示范→完成→独立），把 `scaffold_level` 作为 per-concept 状态，而不是全局 `guided/strict` 开关。
- `guidance_mode` 只做会话默认值；`strict` 只给高掌握或明确要求者；`scaffold_level` 由 BKT + 连续成功/失败 + 自解释质量驱动。
- 示范必须"同构但不同题"，避免直接给当前作业答案；`scaffold_level >= 2` 时抑制 L4/L5。
- 用 within-subject 小实验验证：两篇同难度文本/两组题，A 用 guided、B 用 strict，至少 6 个 session；看首次独立成功率、提示依赖、迁移、7 天保持、挫败率。
- 这条不改变 P0 范围（P0 仍先验证解析/检索/隔离），但应在 P2 教学闭环前完成设计与小实验。

**变更记录**：本次已按此条补入 DESIGN.md §12.9 与 ADR-12；F11 保留为设计变更依据。

## 4. 量化一致性核查

把设计里的数字拿出来对一遍。不是挑错，而是确认"排期和容量"有没有隐藏的 2× 误差。

| 项 | 设计值 | 复核计算 | 判断 |
|---|---|---|---|
| 总页数 | 361,862 | 分类表相加 = 361,862 | 一致 |
| 影印页 | 330,519（91.3%） | 330,519 / 361,862 = 91.3% | 一致 |
| 文字版页 | 25,839（61 本） | 25,839 / 61 ≈ 424 页/本 | 合理 |
| 影印 + 文字 | 330,519 + 25,839 = 356,358 | 与 361,862 差 **5,504 页** | **未解释**；应有 5,504 页"混合/其他" |
| OCR 工时 | 92–184 h | 330,519 / 92–184 h = 0.5–1.0 页/秒 | 与 §8.2 的 1–2 页/秒 **口径冲突** |
| chunk 数 | 43 万 | 430,000 / 361,862 ≈ 1.19 块/页 | 对全库偏低但可能；需说明是"全库"还是"首批" |
| 向量占用 | 1.7 GB | 430,000 × 1024 × 4 B = 1.76 GB | 一致 |
| HNSW 后 | 3–4 GB | 1.7 GB × 2–2.4 | 合理 |
| P0–P3 工时 | 29 + 74 + 70 + 70 = 243 h | §23.7 合计 210 h | **口径不同**（是否含 P0），需统一 |
| P1-0 | 50 轮 × 3 模型 = 150 轮，14 h | 5.6 min/轮（含判分） | 偏紧但可行 |
| §24.6 全量 | 3 模型 × 3 次 × 100 轮 = 900 轮 | 6–10k token/轮 = 5.4–9M token | 成本可接受，时间可能 20 h+ |
| P2-6 | 50 段对话，6 h | 7.2 min/段 | **偏乐观**，10–15 h 更现实 |
| P3-3 | 史记一册竖排 + 注文分离，24 h | 研发 + 调参 + 抽检 | **明显偏乐观**（见 F6） |
| p95 | < 8 s | 检索 0.5 s + 远端 LLM 首 token/生成 | 对 API 模型偏乐观（见 F7） |
| 上下文 | < 12k token | 系统 800 + 状态 300 + 检索 6k + 最近 4 轮 2k ≈ 9.1k | 留有余量，合理 |
| 引用 | 100% 可回溯，95% 原文一致 | 5% 引用可能错 | 对教学场景，95% 偏低；建议 99% 或"逐条页图核验 S 级引用" |
| 泄漏率 | < 10% | 10 次里 1 次泄题 | **偏高**；建议非施压 < 2%，施压 < 5% |
| 复盘准确率 | 30 条 ≥ 80% | 95% CI ≈ ±14% | 样本不足，需 60–100 条 |
| E: 空间 | 465 GB，剩 50.6 GB | 本次未见 E: | **环境不满足**（见 F4） |
| D: 空间 | 499 GB 可用 | 实测 496.3 GB 可用 | 基本一致 |
| GPU/RAM/Python | 4060 8 GB / 31.7 GB / 3.14.7 | 实测 8188 MiB / 31.7 GB / 3.14.7 | 一致 |
| DSH | 0.2.1-rc.3 | `dsh --version` = 0.2.1-rc.3 | 一致 |

**结论**：环境与依赖的硬事实大部分准确；排期与吞吐的软数字有 2× 级别的不确定，且 5,504 页的差额需要一个解释。P0 的 Gate 应该建立在这些数字的实测上，而不是继续推算。

## 5. 解析与 OCR：先做基准，再谈 801 本

### 5.1 60 页基准怎么设计

| 组 | 页数 | 来源 | 必含 |
|---|---:|---|---|
| 竖排古籍 | 20 | 《史记》一册 + 《十三经注疏》一册 | 双行注、校勘记、异体字、无标点 |
| 横排影印 | 20 | 数学/物理各 10 | 公式、表格、双栏、页眉页脚 |
| Steadman | 20 | 希腊 10 + 拉丁 10 | SPIonic、Gentium、NewAthenaUnicode、GFSPorson |

每组人工转写 2–3 页做金标，其余做"可读性/结构"抽检。

### 5.2 指标与门槛

| 指标 | 测法 | P0 门槛 | 不达标动作 |
|---|---|---|---|
| CER | 人工转写对比 | 竖排 ≤ 5%；横排 ≤ 3%；Steadman ≤ 1% | 竖排降级为页图引用；横排查 OCR 参数 |
| 阅读顺序 | 段落首尾对照 | 竖排列序正确 ≥ 95% | 换列切分算法 |
| 注文分离 | 50 页标注 | 错分 ≤ 10% | 推迟竖排自动引用 |
| 公式可编译 | LaTeX 编译/KaTeX | ≥ 90% | 公式只做页图，不进计算 |
| 吞吐 | 100 页计时 | ≥ 0.3 页/秒（CPU） | 调整按需入库规模 |

**为什么把竖排 CER 门槛放到 5% 而不是 3%**：古典汉语的异体字、避讳字、无标点、双行注，决定了 3% 在没有领域微调时不现实；先用 5% + 页图兜底，比追求一个达不到的 3% 更有用。

### 5.3 设计里三个需要改的具体点

1. **`route()` 的 3 页采样**（§8.1）：混合卷（横排前言 + 竖排正文）会被整本误判。改为**逐页判定**，卷级只做先验；`vertical_score` 低于阈值的页走横排。
2. **`GREEK_FONTS` 白名单**（§8.4）：补 SPIonic、Gentium、SymbolMT，并加 Unicode 区块兜底（见 F3）。
3. **`text_norm` 异体字表 500 字**（§8.3）：先测 OOV 率；如果 Top-1000 常用字覆盖不到 95%，检索召回会显著掉。建议先做 1,000 字表，或直接用 OpenCC + 自定义表。

## 6. 答案隔离：全系统最重要的不变量

### 6.1 不变量怎么写

> **任何 `visibility=answer_key` 的 chunk，在任何 hint level < 4 的会话中，都不得进入模型上下文、工具返回值、日志摘要或 UI 引用卡。**

这不是"提示词约束"，而是**数据契约**。验收方式必须是可执行的测试，不是人工检查。

### 6.2 三条实现路径的优先级

| 路径 | 强度 | 代价 | 建议 |
|---|---|---|---|
| A. sidecar 强制 `view` 过滤 | 最强（数据层） | 需要自建检索或改 L1 | **首选** |
| B. L1 三 base + 调用方自律 | 中（依赖配置） | 低 | 仅作过渡，必须加 canary |
| C. 出站 critic 重写 | 弱（依赖钩子） | 中 | 只能兜底；DSH 大概率没有钩子 |

### 6.3 必做的四个测试

1. **canary 检索**：`answer_key` 里埋 `CANARY-7F3A`，用 100 条学生查询跑 `kb_search`，断言零命中。
2. **canary 对话**：50 轮压力对话（含"直接告诉我"），断言输出与上下文无 canary。
3. **autoRetrieve 关闭验证**：不调用任何检索工具，问一个只有馆藏能答的问题；如果模型仍能引用馆藏，说明自动检索没关。
4. **跨 base 越权**：尝试用工具参数、URL、文件名、MCP 资源等路径读 `answer_key`；全部拒绝才算过。

### 6.4 一个容易忽略的泄漏面：注释与翻译

- `translation` 流明显是答案，设计已经隔离。
- `note` 流（注释）经常包含"这里的意思是……"、"即……"，等价于答案；它却是 `student` 可见的。
- 建议：note 块增加 `contains_answer: bool`（人工/LLM 标注 + 抽检），hint level < 2 时不返回含答案的 note；或者把 note 的可见性再分 `note_hint` / `note_full`。

## 7. 教学层：状态机是对的，判定是薄弱点

### 7.1 状态机

§12.1 的状态机是确定性的、可单测的，这是正确的方向；但默认 `ASK` 优先，对新手的适配性见 F11。三个建议：

- `EVALUATE` 不要只输出"正确/部分/错误"，要输出 **判定依据**（引用/工具凭证/规则命中），否则复盘无法归因。
- `DIAGNOSE` 的 2–3 个诊断问题要有"退出条件"：学生答不上来时，不能无限诊断；给一个默认掌握度先开始。
- `ADVANCE` 的"连续 2 次通过"太粗；至少区分"同概念不同题"与"同题重复"。

### 7.2 判定

- 人文的"正确"是论证质量，不是事实对错；§13.3 的四类判定（correct/partial/incorrect/undetermined）方向对，但 `correct` 的条件"与证据一致，且推理链完整"需要 rubric 支撑，否则 LLM 判定会漂移。
- 建议：每个学科包提供 3–5 条 rubric（论点/证据/反驳/表达），判定时先规则、再 rubric、最后 LLM；LLM 只做"哪条 rubric 没满足"的分类，不做最终对错。
- `undetermined` 不是失败，是材料质量信号；§13.7 的 >20% 阈值应触发"补书/重解析"，而不是简单标红。

### 7.3 提示与揭示

- §12.4 的 `may_reveal` 里，`frustration >= 2 and attempts >= 1` 可能过早揭示；建议先跑 30 个模拟学生，统计"首次揭示前的平均尝试次数"，再定阈值。
- L4 "近乎完整推导（留最后一步）"与 L5 "答案 + 讲解"的边界要可判定：L4 的输出不能包含最终结论的符号表达式，否则就是 L5。
- 每次 L4/L5 强制回讲是对的；回讲判定用"关键点命中"而不是整体语义相似，否则学生复述一遍废话也能过。

### 7.4 学习者模型

- BKT 参数未标定，见 F8；先当启发式。
- FSRS 用于词汇是合适的；但希腊/拉丁的词形还原与词典查询是另一套，不要把 FSRS 的"记忆强度"当成"语言能力"。
- 情绪打分用"连续答错、回复变短、出现直接告诉我"是合理的冷启动规则；但"回复变短"在手机输入/考试场景会误判，需结合历史基线。

### 7.5 复盘

- §13 的"冻结快照 → 断言抽取 → 逐条判定 → 归因"是项目里最有差异化的部分，设计得比教学状态机更细。
- 最大风险是"断言抽取"：学生的话经常是疑问、假设、引用老师的话，不是可判定的断言；抽错会导致复盘冤枉学生。
- 建议：断言抽取加"是否为学生自己的主张"分类；疑问/转述/假设一律不进判定，标 `not_a_claim`。
- 归因三分（student/question/material）很好；建议再加 `curriculum`（超纲/前置缺失），否则"学生错"会掩盖"我们选错了题"。

## 8. 计算与沙箱

### 8.1 验证协议

§14.3 的"提议 → 执行 → 比对 → 凭证"方向正确。三个加固点：

1. **符号等价不是 `simplify` 一件事**：`equals()` 带假设、精确化简、数值采样、定义域检查，四步都过才 `verified`；否则 `unknown`。
2. **数值容差要分学科**：数学 1e-9，物理按有效数字（1e-3–1e-6），金融/统计另设；不要一个 1e-6 打天下。
3. **计算凭证要含输入来源**：`chunk_id` + `formula_conf`；如果公式来自 OCR 且 `conf < 0.9`，凭证标 `unverified_formula`，禁止把结论说成"已证明"。

### 8.2 沙箱

- 子进程 + `timeout` 在 Windows 上不够；用 Job Object（见 F9）。
- "禁网"要在进程/容器层做，不要只在 Python 里 `socket.disable`；模型生成的代码可以 `ctypes` 绕过。
- 学生代码升级到 Windows Sandbox / WSL 是对的；但默认的 `compute_python` 也执行模型生成的代码，必须同等对待，不能因为"是模型不是学生"就放宽。
- 审计日志记录：谁、哪个会话、哪段代码、退出码、资源峰值；不要记录完整 stdout（可能含答案）。

### 8.3 Wolfram / Lean

- Wolfram Engine "开发免费、部署需授权"需要核对具体条款；如果是个人本地使用，通常可接受，但不要在开源发布物里默认依赖。
- Lean 放 P3 合理；不要在 MVP 承诺"形式验证"，Mathlib 对人文/古典语言没有覆盖，对本科分析也有限。
- 如果上 Lean，先定义"验证什么"：陈述可证、证明闭合、无 `sorry`；不要用 Lean 生成教材证明。

## 9. DSH 集成：8 项 API 与 fallback

§16.9 列了 8 项必须核对的 API。这是对的，但**只有第 8 项写了 fallback**（critic 方案），其余 7 项没有。建议补一张 fallback 矩阵：

| # | 核对项 | 若不存在/行为不符 | Fallback |
|---|---|---|---|
| 1 | `defineTool` schema | 编译/校验失败 | 用原始 JSON Schema 注册；参数在 sidecar 再校验 |
| 2 | `tools/post-execute` 替换 content | 不能改写 | 在 sidecar 返回前裁剪；Host 只做透传 |
| 3 | `systemPrompt.context` 回放 | 刷新后状态丢失 | 状态写 session event + 自定义节点重放 |
| 4 | `ConversationNodeDefinition` | 客户端不能渲染 | 通用卡片 + 右侧栏；不阻塞教学 |
| 5 | `ctx.jobs.start` 进度 | 无进度事件 | 轮询 sidecar `/v1/jobs/{id}` |
| 6 | `ctx.storage` 形态 | 不能持久化 | 学习者模型存 sidecar SQLite，Host 只读 |
| 7 | 本地配置/token | 读不到文件 | 环境变量注入；启动脚本写 `DSH_SIDECAR_TOKEN` |
| 8 | 出站消息钩子 | 不存在 | **数据层隔离 + critic 兜底**；不要承诺零泄漏 |

**建议**：P0 先写一个 `capability-probe` 插件，只做 8 件事的探针，2 天内出结论；不要在教学代码里边写边试。

另外两点：

- `socratic-core < 1,500 行` 的估算偏乐观：5 个服务 + 11 个工具 + 6 个钩子 + sidecar 客户端 + 配置，2,000–3,000 行更现实；这不是问题，但排期要按 2–3k 行估。
- 客户端自定义节点是最大 UI 风险；如果 `ConversationNodeDefinition` 不可用，引用卡/提示级别/复盘报告都要退回通用卡片，体验会降级。P0 就要验证，不要等到 P2。

## 10. 复用、许可与开源

### 10.1 AGPL 是决策，不是细节

- `dsh-knowledge@0.5.2` 确认 AGPL-3.0；依赖含 mupdf（AGPL）、ppu-paddle-ocr、onnxruntime-node 等。
- 进程内 `ctx.knowledge` 调用与"独立 HTTP 服务"在法律上是两件事；不要把"我们只是调用工具"当成免责。
- 三条路：
  1. L1 独立进程 + HTTP：Host 插件保持 MIT；代价是部署多一个服务、延迟 +10–30 ms。
  2. 接受 AGPL：整个组合 AGPL，放弃 MIT 发布。
  3. Plan B 自建：60–80 h，完全 MIT，但要自己维护检索。
- 建议在 P0-0 前做选择，不要等到开源发布时才发现。

### 10.2 PyMuPDF 与 pypdfium2

- 设计已经指出：PyMuPDF AGPL，pypdfium2 Apache/BSD。这是对的。
- 但 Steadman 的字体分流依赖 span 级字体信息；pypdfium2 的文本抽取 API 是否能提供同等粒度的 font/bbox，需要 P0 实测。如果不行，"MIT 发布"与"字体分流"二选一：
  - 选 MIT：用 pypdfium2 + Unicode 判定，可能损失部分字体信息；
  - 选字体：用 PyMuPDF，插件 AGPL。
- 这个取舍要在写第一行解析代码前定，不要事后返工。

### 10.3 开源边界

- §16.11 / §23.8 的边界（不 fork AGPL、不带语料、fixture 用公版）是成熟的。
- 建议再加一条：**开源仓库不含任何 `E:\PDF` 的书名列表/哈希清单**；馆藏清单本身可能暴露来源与版权信息。用合成书目做测试。

## 11. LLM 选型与长程协议

### 11.1 方向是对的

§24 的 D1–D7、50–100 轮压力脚本、12 类工具故障注入，是这份设计里最专业的部分之一。教学 Agent 的失败确实只在长程暴露：状态漂移、负向约束侵蚀、工具格式退化。

### 11.2 三个需要修正的点

1. **D1 "状态保持"测的是什么**：如果每轮都把状态摘要注入 `systemPrompt.context`，模型不需要"记住"，测的是"会不会用注入的状态"，不是"长程记忆"。两者都重要，但要分开命名：
   - D1a 状态利用（有注入时是否遵守）；
   - D1b 状态回忆（不注入时是否记得，仅作参考，不作硬门槛）。
2. **CVR ≤ 5% 对"不给答案"太松**：5% 意味着 20 轮里可能泄 1 次。建议分场景：
   - 非施压：≤ 1–2%；
   - 施压：≤ 5%；
   - 任何 L4 前出现最终答案：0（硬失败）。
3. **900 轮全量测试的时机**：P1-0 只做 50 轮 × 3 模型（150 轮）是合理的；900 轮应放在 P2 教学闭环跑通之后，否则测的是"prompt 在真空里"的表现，不是系统表现。

### 11.3 p95 与模型位置

- 教学主模型在远端，p95 < 8 s 受网络与 provider 负载影响；建议改成"首 token < 3 s、完整 < 12 s"，并在 UI 上用流式。
- critic 用不同族模型是对的；但"不同族"不等于"不同错"，仍要人工校准 50–100 条。
- 本地 8 GB 只做分类/情绪/语言识别，不要试图本地教学；§24.3 的判断正确。

## 12. 评测：指标要分层，样本要够

### 12.1 现有指标的问题

- **聚合指标掩盖分层失败**：100 条查询的 recall@10 0.85 可能由 80 条中文 + 20 条希腊平均而来；希腊可能只有 0.5。
- **没有按 stream 分层**：`text` / `gloss` / `note` / `apparatus` 的召回难度完全不同；注文分离差会直接拉低 note 的召回。
- **没有按解析质量分层**：同一本书，高质量页与低质量页的召回应分开统计；否则解析器的进步会被平均掉。
- **没有成本指标**：100 轮会话的 token/费用、每轮检索次数、计算调用次数。
- **没有计算审计**：多少"计算结论"有凭证、多少是口头、多少凭证与结论不一致。

### 12.2 建议的指标矩阵

| 维度 | 指标 | 分层 |
|---|---|---|
| 检索 | recall@10、nDCG@10、citation precision | 语言 × stream × 解析质量（高/低） |
| 引用 | 页图核验通过率、书名级定位准确率 | S/A/B 级来源 |
| 教学 | 泄漏率、提示层级分布、回讲通过率 | 学科 × 提示级别 × 是否施压 |
| 复盘 | 判定准确率、归因准确率、undetermined 率 | 错误类型 × 归因类型 |
| 计算 | 凭证覆盖率、假阳性率、超时率 | 工具 × 学科 |
| 系统 | p50/p95、token/轮、成本/轮、queue wait | 是否含检索/计算 |
| 学习 | 前后测增益、7 天保持率 | 概念 × 学科 |

### 12.3 样本量

- 30 条复盘样本估 80% 准确率，95% CI 约 ±14%；建议 60–100 条，或明确报告 CI。
- 100 条检索查询估 0.85，CI 约 ±7%；可接受，但要分层后再看。
- 50 段对话估"泄漏 <10%"，CI 很宽；建议至少 100 段，或把"泄漏"当作二项比例报告置信区间。

## 15. 结论与三个架构级建议

### 15.1 结论

- **设计可执行**，ADR 质量高，复用边界清楚；不是"想法很大、落不了地"的项目。
- **关键路径是数据**：竖排解析、注文分离、OCR 吞吐、引用核验；代码不是瓶颈。
- **最大架构风险是答案隔离的"最后一公里"**：L1 没有 chunk 级可见性，DSH 没有出站改写钩子，两者叠加使 ADR-05 只能部分成立。
- **最大排期风险是竖排与 OCR 的工时**：24 h / 92–184 h 这两个数字需要用实测替换。
- **教学范式缺一层**：默认 ASK-first 对新手不友好；本次已补 §12.9/ADR-12（F11），但需 P2 小实验验证。
- **建议批准 P0，但把 P0 当否决性实验**；不要先写教学 UI，也不要先导入 801 本。

### 15.2 如果只改三件事

1. **收窄 MVP**：人文 + 中文 + 一本书 + 一个学生；Steadman 作为第二垂直；理工/乐理后置。G6/G7 降为产品目标，不写进 MVP 验收。
2. **把答案隔离变成 sidecar 契约**：`/v1/search` 必填 `view`，在 SQL/向量层过滤；`answer_key` 不对模型暴露任何工具；canary 测试进 CI。不要依赖 `dsh-knowledge` 的配置或提示词。
3. **先做 60 页解析基准，再谈 801 本**：竖排/横排/Steadman 各 20 页；CER、阅读顺序、注文分离、吞吐四项达标，才进入 P1 全量入库。

F11 的 §12.9 是并行改动，不改变这三条的优先级；它决定 P2 教学闭环是否对新手成立。

### 15.3 什么情况下应该停

- 竖排 CER >8%，且页图 + 人工引用也无法满足教学；
- 注文错分 >15%，且三流分离调不到 10% 以内；
- `dsh-knowledge` 无法关闭 autoRetrieve，且无法在 chunk 级隔离答案；
- DSH 8 项 API 中 ≥3 项不可用，且 fallback 会导致核心体验不可接受；
- 计算沙箱出现任一逃逸。

停不是失败；在 P0 停，比在 P3 发现"竖排不能引用"便宜 10 倍。
